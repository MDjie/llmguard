# 词库、规则与检测机制复核

核对时间：2026-09-05 09:10，Asia/Shanghai。代码基线：`ad09fb4`，并检查当前工作区文件。

本次依据当前源码、词库文件、本地项目数据库的只读查询及重新执行的测试。数据库结论仅适用于本项目 `.env.local` 指向的本地实例，不代表其他部署环境。

## 1. 核心结论

当前本地生效配置是“词法/正则规则 + 内置特征检测 + 规则化上下文判断”。代码已经实现可选的外部语义分类器，但当前生效策略包没有配置它，也没有语义检测节点。因此，不能把当前本地运行状态描述成已启用大模型上下文语义审核。

需要修正此前两种说法：

- “没有语义模型调用链”不准确。调用适配器、策略编译配置及调度节点均已存在，只是当前实例未启用。
- “新增 JSONL 由根目录 Python 脚本导入数据库”不准确。根目录脚本处理历史 Sensitive-lexicon 资源；新增独立词库走 `scripts/content-safety/` 流水线，目前只生成候选数据和离线影子产物。

“项目文件中存在”“进入数据库”“被生效策略包加载”是三个不同状态。

## 3. 检测链路究竟如何工作

### 3.1 主要接口

`/api/detect` → `detectWithGuardEngineV2` → 加载经验证的策略包 → `createEngineForPolicyBundle` → 文本规范化与 DAG 调度 → 各检测器 → 风险聚合与输出处理。

证据：[接口入口](</E:/大模型安全/大模型护栏/src/app/api/detect/route.ts:58>)、[兼容入口执行引擎](</E:/大模型安全/大模型护栏/src/lib/detection/v2-compat.ts:245>)、[策略包构造检测器](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/from-policy-bundle.ts:63>)。

| 能力 | 实现方式 | 当前含义 |
| --- | --- | --- |
| 敏感词检索 | Aho–Corasick 多模式匹配、精确/包含/前后缀匹配 | 词法检测 |
| 模糊变体 | 有界编辑距离等机制 | 仍属字符串近似匹配 |
| 正则、隐私、提示攻击 | 模式和校验逻辑 | 规则/特征检测 |
| 新闻、引用、医疗、教育、否定等上下文 | 正则、邻近窗口、固定条件与置信值 | 上下文感知规则，不是模型推断 |
| 推理攻击归因 | 步骤、目标、方法、隐藏意图等特征组合 | 名称含“推理”，实现仍是特征规则 |
| 外部语义分类 | HTTP 分类调用，验证模型身份、标签与置信度 | 已实现可选适配，当前绑定包未启用 |

证据：[词法匹配](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/lexical-matcher.ts:26>)、[上下文分类](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/intent-context.ts:87>)、[推理攻击特征](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/reasoning-attack-detector.ts:25>)。

### 3.2 语义模型接入条件与局限

构建时读取 `SEMANTIC_CLASSIFIER_CONFIG_JSON`，将模型标识、版本、哈希、地址、标签阈值等写入策略包。运行时只有包携带该配置且其 DAG 引用对应检测器，才会注册并调度外部分类器。请求通过 `safeFetchJson` 发出，并校验响应的模型身份和条目覆盖。

`SHADOW` 模式输出观察记录，不参与风险命中聚合；`ENFORCE` 模式将超过阈值的分类结果转成风险命中，并要求失败时关闭放行路径。

默认语义节点的条件是 `WHEN_NO_BLOCKING_MATCH`：前序已产生达到拦截阈值的命中时，语义节点会跳过。因此，即使接入模型，当前默认流程也不是“所有敏感词命中都交给语义模型复核后再决定”。如果目标是用模型纠正规则误杀，还需要设计待确认信号和模型复核决策逻辑。

证据：[分类请求与响应处理](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/semantic-classifier.ts:44>)、[配置读取](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/semantic-classifier.ts:190>)、[条件调度](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/default-dag.ts:190>)。

旧 `dynamic-engine` 中仍有 Judge 调用分支，`src/lib/llm` 中也有模型模块；本次源码引用搜索未发现这些旧检测函数被当前主要检测入口调用。配置旧 Judge 页面不等价于启用 V2 的 `semanticClassifier`。

### 3.3 多轮上下文

`/api/v1/guard/evaluate` 使用 `evaluateWithSessionContext`：读取安全记忆，将历史窗口与当前文本组合再次检测，并推进会话风险状态。若语义分类器已配置，它可以在这一链路的合并文本视图上工作。

`/api/detect` 的兼容函数直接执行 `engine.evaluate`。传入 `sessionId` 本身不会让此函数自动读取并拼接安全记忆。两条入口的多轮上下文能力目前不一致。

证据：[V1 接口](</E:/大模型安全/大模型护栏/src/app/api/v1/guard/evaluate/route.ts:97>)、[安全记忆检测](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/session-context.ts:113>)。

## 4. 白名单核对

当前新编译路径要求白名单具有审批人、指定风险维度、目标规则 ID、适用方向及生效/失效时间。运行时按匹配位置判断：完整白名单短语只能抑制它覆盖的目标词法命中。同一文本在短语之外出现的另一次风险命中继续保留；强制拒绝规则不豁免。例外只传给 `RuleDetector`，不会关闭独立语义模型或其他检测器。

但这描述的是已经实现的机制：本地数据库和绑定包白名单记录目前均为 0，新 JSONL 中的 12 条尚未发布。

运行时仍保留没有 `targetRuleIds` 的历史兼容分支：匹配到历史例外后，可以跳过整个对应风险规则。新编译器会拒绝新增这种不完整例外，但旧格式包的兼容能力仍存在。当前绑定包没有例外，本次没有发现该分支正在生效。

证据：[编译约束](</E:/大模型安全/大模型护栏/src/lib/policy-bundle/compiler.ts:158>)、[历史例外与局部抑制](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/rule-detector.ts:177>)。

## 5. 已发现的衔接问题

### 5.1 新风险编码未接入现有上下文抑制集合

影子编译器将 `CN.A…`、`HARM.…` 等风险 ID 原样写入规则；`RuleDetector` 的上下文抑制集合却使用 `sensitive_compliance`、`adult_content` 等旧编码。当前集合不覆盖新增影子规则的编码。

本次使用无害标记进行内存复现：文本 `news report mentions risk-marker`、相同 contains 规则、相同分值。`classifyContextRole` 返回 `news`；使用旧风险编码 `sensitive_compliance` 时产生 0 条命中，替换为 `CN.A1.01` 后产生 1 条命中。

这证明上下文抑制映射不一致，不代表每条此类文本最终都会被拦截；最终动作还受分值和聚合影响。问题目前位于候选/影子接入路径，正式晋级前需要修复并补充同文同义、不同风险编码的回归测试。

证据：[风险集合与条件](</E:/大模型安全/大模型护栏/src/lib/guard-engine-v2/rule-detector.ts:16>)、[影子规则风险编码](</E:/大模型安全/大模型护栏/scripts/content-safety/compile-shadow-bundle.mjs:73>)。

### 5.2 “需要语义确认”尚未成为执行约束

词条中的 `semantic_confirm`、`score_only` 等 `action_hint` 目前写入影子包的 provenance，检测器并不依据它们决定是否等待模型复核。编译器对普通词统一使用 contains，并生成普通风险规则。因此，不能把词条元数据里的“语义确认”理解成已经实现的检测动作。

影子包明确 `enforcementAllowed=false`、`signed=false`，现有生产加载边界仍应保留；正式接入时需要显式映射词条处理方式、风险分类、适用上下文及执行动作。

证据：[匹配方式](</E:/大模型安全/大模型护栏/scripts/content-safety/compile-shadow-bundle.mjs:33>)、[actionHint 保存位置](</E:/大模型安全/大模型护栏/scripts/content-safety/compile-shadow-bundle.mjs:83>)。

### 5.3 历史 SQL 导入格式与当前编译器存在兼容缺口

根目录旧 Python 工具将整组词写入 `detection_rules.config.keywords`，其 INSERT 列表不含 `pattern`；当前编译器只接受启用且具有非空 `pattern` 的传统规则，或走已治理的 `keywordRules`。本次检查没有找到自动展开这批 `config.keywords` 的当前加载逻辑。

因此，不能仅执行旧 SQL 就宣称 15 组词库已进入当前检测器。应转成规范词条/规则并核对最终策略包，而不是依靠旧导入脚本的成功返回。本地数据库实测也没有这些旧资源的导入记录。

证据：[旧导入 INSERT](</E:/大模型安全/大模型护栏/import_sensitive_lexicon.py:242>)、[当前编译过滤](</E:/大模型安全/大模型护栏/src/lib/policy-bundle/compiler.ts:134>)。

### 5.4 不能承诺“没有误杀”

当前上下文识别使用固定模式，无法完整理解否定范围、引用目的、反讽、隐晦意图等。外部候选也尚未审核。现有通过的测试验证了有限的实现行为，不能推导开放输入上的零误杀或零漏检。

发布验收应按业务场景分别衡量误杀率、漏检率、语义复核覆盖率、白名单越权抑制和模型超时降级结果，同时保留真实业务反例与独立评测集。
