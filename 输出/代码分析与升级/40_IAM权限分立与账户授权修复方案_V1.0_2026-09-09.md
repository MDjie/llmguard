# IAM 权限分立与账户授权修复方案

日期：2026-09-09；适用基线：当前 `main` 工作区。本文基于产品设计、现有代码和已通过的认证/接口/租户相关测试形成，作为 IAM 修复的实施与验收依据。本文不修改生产账户、角色、租户、应用或策略包。

## 1. 结论和修复目标

当前系统已经具备本地账户登录、六种固定角色、统一 API 权限校验、会话撤销、租户/应用上下文和部分异人审批能力，不能称为“无权限管理”。但它尚未达到设计文档要求的“三员分立、按租户/应用授权、RBAC + ABAC、完整账户开通和高风险异人审批”。

本次修复目标是建立可用且可审计的账户授权闭环：

1. 角色只授予职责所需权限，系统、安全、审计三员不能通过一个日常账户汇聚全部高风险能力。
2. 每个可登录用户必须拥有显式、有效的租户和应用授权；未授权应用既不能出现在列表中，也不能被切换或以请求头访问。
3. 创建、变更、禁用和删除账户都在租户/应用范围内完成并留下审计记录；新账户首次登录可实际成功。
4. 策略发布、长期白名单、证据导出、工具高风险动作等继续采用异人审批，且由统一规则验证，而不是只依赖页面按钮。
5. 以可迁移的方式兼容历史 `admin`/`user` 角色和值，避免一次发布锁死既有管理员或越权开放全部应用。

## 2. 设计要求与当前事实

产品设计明确规定系统管理员、安全管理员、审计管理员三员分立；策略发布、长期白名单、模型上线、证据导出和高风险动作要异人审批；租户、应用、环境和数据域需要四层隔离。详细设计进一步要求角色决定动作、属性约束 tenant/app/data classification/environment/ownership。

当前的有效能力如下：

| 能力 | 当前实现 | 结论 |
| --- | --- | --- |
| 固定角色 | `SYSTEM_ADMIN`、`SECURITY_ADMIN`、`AUDIT_ADMIN`、`BUSINESS_OPERATOR`、`APP_DEVELOPER`、`READ_ONLY` | 已有基础 RBAC |
| 后端授权 | 所有常规 API 经 `withApiSecurity` 认证并按 `permission` 返回 401/403 | 有效，不能只靠前端隐藏 |
| 菜单与部分页面 | 读取 `/api/auth/me` 的权限并过滤导航、禁用部分编辑控件 | 仅为体验层，后端校验仍是边界 |
| 账户状态变化 | 改角色、禁用或改密时递增 `tokenVersion`，旧会话失效 | 有效 |
| 租户上下文 | 登录认证会验证 `tenant_memberships`，业务查询大量使用作用域谓词 | 已有基础隔离 |
| 异人审批 | 导出、白名单、工具调用、词典/模板/发布集存在部分申请人与审批人不同的校验 | 可复用，但尚未统一治理 |

## 3. 根因分析

### 3.1 系统管理员实际成为日常超级管理员

`SYSTEM_ADMIN` 被配置为 `PLATFORM_PERMISSIONS` 全集，因而同时具备用户管理、策略编写/审批/发布、原文访问、安全处置、审计读取和导出能力。这与“三员权限互斥”直接冲突。虽然 `users.role` 只有一个值，形式上不能同时存储三个角色，但“全权限系统管理员”绕过了这个约束。

### 3.2 策略治理权限与角色矩阵脱节

新版词典、响应模板和发布集接口分别要求 `policy:write`、`policy:approve`、`policy:publish`，而 `SECURITY_ADMIN` 目前只有 `policy:read`、`policy:manage`。权限没有包含关系，因此安全管理员无法完成设计上应承担的策略编写流程。现有旧策略接口使用 `policy:manage`，造成同一职责在新旧接口的权限语义不一致。

### 3.3 新建账户没有在同一事务内获得登录范围

`POST /api/users` 只插入 `users`，不会插入 `tenant_memberships`。但每一次登录后的请求认证都必须通过 `resolveUserTenantScope` 找到活动租户、活动应用和成员关系。结果是新建账户即使密码正确，也无法完成可用会话范围的解析。这是开户流程断裂，不是单纯的页面缺失。

### 3.4 当前成员模型没有真正限制到应用

`tenant_memberships` 只保存 `default_application_id`。当用户显式选择其他应用时，`resolveUserTenantScope` 仅校验该应用属于同一租户，不校验用户是否被授予该应用；`GET /api/applications` 同样返回整个租户的应用列表。因此同一租户内的成员可切换并访问任意活动应用，应用级隔离实际上未实现。

### 3.5 账户管理缺少可操作的控制台和授权对象

已有 `/api/users` 管理接口，但导航和路由中没有用户管理/角色管理页面。接口也没有输入租户、默认应用或可访问应用集合，因而即使直接调用接口创建用户，也无法完成安全开户。角色与权限矩阵固定在代码中，没有受控的角色配置或角色变更审批记录。

### 3.6 ABAC、企业身份和应急控制停留在数据字段或规划层

应用已有 `environment`、`dataClass`、`owner` 等属性；主体类型中预留了 `userGroupIds`，但本地认证不加载用户组或数据域授权，也没有以这些属性作统一资源访问判定。代码库未发现 OIDC/SAML、MFA/WebAuthn/TOTP、应急账号双人启用的可用登录流程。因此目前只有角色 + 租户上下文，不能宣称已完成 RBAC + ABAC 或企业 IAM。

## 4. 目标授权模型

### 4.1 职责分离的角色基线

保留六种产品角色，但取消任何日常角色的“全部权限”语义。角色是动作集合，租户/应用授予是资源边界；两者必须同时满足。

| 角色 | 职责和允许动作 | 明确不授予 |
| --- | --- | --- |
| 系统管理员 | 用户和成员关系、租户/应用生命周期、平台配置、应用凭据和可观测性 | 策略内容编写/审批/发布、原始证据读取、审计导出审批 |
| 安全管理员 | 安全告警处置、策略草稿/校验/测试、受控模型与工具安全配置 | 用户与角色管理、审计导出审批、自身提交内容的审批 |
| 审计管理员 | 审计读取、导出申请/审批、策略与发布证据复核、合规报表 | 策略内容修改、模型/应用配置、用户与角色管理 |
| 业务操作员 | 在获授应用内使用护栏、读取获准的运行记录和策略摘要 | 改策略、改应用、读取原文、审批、导出 |
| 应用开发者 | 在获授应用内接入、使用和轮换自己的应用凭据 | 全租户应用管理、策略发布、审计导出、原文访问 |
| 只读用户 | 在获授应用内查看已允许的策略摘要、历史和状态 | 所有写入、审批、导出和凭据操作 |

`policy:manage` 只作为旧接口兼容权限，逐步拆分为 `policy:write`、`policy:approve`、`policy:publish`。发布路径不得因为拥有 `policy:manage` 自动获得审批或发布权。系统管理员的初始引导账户仅用于创建首个职责账户和恢复受控访问，不作为日常运营账户。

### 4.2 资源授权与属性约束

新增显式“用户—应用授予”关系。用户可有多个租户和多个应用授予，但每一项必须明确记录，不使用“同租户全部应用”的隐式推导。每项授予至少包含：`userId`、`tenantId`、`applicationId`、状态、默认标志、授予人、授予时间、撤销人、撤销时间和版本号。

后续 ABAC 扩展在该关系上增加或关联以下约束：允许环境、最高数据分级、部门/所有者范围、用户组、有效期和用途。请求同时通过以下三道判断才可操作资源：

`角色拥有动作权限` AND `用户被授予目标租户/应用` AND `资源属性满足数据域/环境/用途约束`。

### 4.3 审批职责

统一审批约束为：申请人与审批人必须不同；审批者具备指定审批权限；审批记录绑定资源版本、租户、应用、用途、有效期和最终执行参数；状态变更使用条件更新避免并发重复审批。当前导出、白名单、工具调用和部分策略治理已有可复用实现，应抽取公共服务并补齐其余高风险路径。

## 5. 分阶段实施方案

### P0：先修复越权和职责冲突

1. 在 `src/lib/api-security/types.ts` 固化权限归类，并在 `src/lib/auth/authorization.ts` 重建最小权限矩阵。删除 `SYSTEM_ADMIN: PLATFORM_PERMISSIONS`；保留旧角色别名仅用于迁移读取。
2. 统一策略权限：安全管理员拥有草稿、校验和测试所需的 `policy:write`；审批和发布分别授予独立职责角色。逐项修改旧 `policy:manage` 接口，或在兼容期内由明确的映射函数处理，禁止隐式全量包含。
3. 审计所有高风险路由：策略发布/回滚、白名单审批、模型上线、Provider 凭据、原文/媒体证据、导出、应用凭据、角色变更和应急账号。每项明确申请权限、审批权限、申请人/审批人不可相同、资源版本绑定和审计事件。
4. 为系统管理员移除策略和审计敏感权限前，提供一次性受控迁移命令：创建首个安全管理员和审计管理员，并生成“待完成职责拆分”告警。不得静默降权造成无人可管理。

### P1：修复开户与应用级作用域

1. 新建数据库迁移，新增 `user_application_memberships`（名称可在实施时按现有命名规范确定）。约束 `(user_id, tenant_id, application_id)` 唯一；外键确保应用属于租户；记录生命周期和审计字段。
2. 将现有 `tenant_memberships.default_application_id` 回填为一条应用成员记录。迁移前输出计数和异常清单；若用户默认应用不存在、停用或跨租户，拒绝切换到新认证逻辑并先修复数据。
3. 将 `resolveUserTenantScope` 改为只接受显式的应用成员授予。`GET /api/applications` 只返回主体已获授的活动应用；`POST /api/auth/scope` 对未授予的应用返回 404/403，不能依赖前端下拉框保护。
4. 扩展创建用户请求，要求指定一个活动租户、至少一个活动应用和默认应用；在一个数据库事务内写入用户、成员关系、密码历史/首次改密状态与审计事件。创建失败时全部回滚。
5. 扩展更新用户请求，支持受控增删应用授予、变更默认应用、禁用成员关系和设置有效期。撤销任一授予或角色时递增用户会话版本，并使已签发范围 Cookie 立即失效。
6. 用户列表、详情、修改和删除按管理者可管理范围过滤；跨租户全局枚举只能由专门的平台管理能力使用，且需要独立审计。普通租户管理员不能看到未授权租户的账户资料。

### P2：补齐管理控制台与审计可见性

1. 新增“用户与授权”页面，仅在 `iam:users:read` 时展示菜单。页面显示角色、状态、首次改密状态、租户/应用授予、有效期、最近登录和最近授权变更。
2. 新建/编辑弹窗必须先选择租户和应用，再选择角色；默认应用必须属于已选应用；不允许提交空授权。前端按钮仅用于减少误操作，所有规则仍由 API 和数据库强制执行。
3. 将角色、成员关系、禁用、密码重置、应用凭据、审批决定写入不可篡改审计链，记录操作者、对象、前后摘要、理由、租户/应用、请求 ID 和时间。
4. 新增“待审批”视图，按审批类型区分策略、白名单、导出、工具和高权限账户变更；审批页必须隐藏本人提交的待办或明确显示不可审批原因。

### P3：落实 ABAC 和企业身份

1. 以 `principal.attributes` 或等价强类型对象承载用户组、部门、允许环境、最大数据分级、用途和有效期；认证时从受控数据库或企业 IdP 加载，禁止接受浏览器自报属性。
2. 在 API 安全层和数据访问服务引入资源属性判定接口，先覆盖原文证据、导出、数据目录、Provider 凭据和生产应用配置，再扩展到普通历史记录。每个数据查询保持 `tenantId + applicationId` 谓词。
3. 接入企业 OIDC/SAML，保留本地账户仅作为经批准的恢复路径；生产管理登录启用 MFA（WebAuthn 或企业 IdP MFA 声明），会话记录认证强度和 IdP 会话标识。
4. 建立应急账号工作流：默认禁用、离线保管、两名不同职责人员批准后短时启用、操作全量告警、到期自动禁用和事后复核。不得把普通 `SYSTEM_ADMIN` 当作应急账号。

## 7. 验收标准

### 必须新增的自动化用例

1. 六种角色的权限快照测试：每个允许和拒绝的高风险动作均有断言；系统管理员不再获得策略审批/发布、审计导出和原文访问的组合权限。
2. 安全管理员可创建、校验和测试策略草稿；无法审批自己提交的策略，且不能绕过 `policy:approve`/`policy:publish`。
3. 新建用户在同一事务写入一个默认应用授予，首次改密后可登录；创建时缺租户、无应用、默认应用不在集合、停用应用或跨租户应用均失败且不留下用户残留记录。
4. 用户仅能看到并切换获授应用；伪造 `x-guard-application-id`、范围 Cookie 或请求体中的其他应用 ID 必须被拒绝。覆盖同租户不同应用、不同租户和授予撤销后旧会话三种反例。
5. 角色、应用授予、禁用或删除后，旧 Cookie、Bearer Token、范围 Cookie 都不可继续访问原范围。
6. 导出、白名单、工具、词典/模板/发布集、模型上线和高权限账户变更分别验证申请人与审批人不同、并发二次审批失败、资源版本变更后旧审批失效、到期审批失效。
7. 用户管理 API 的列表、详情、修改和删除按授权范围过滤；无 `iam:users:*` 权限返回 403，匿名请求返回 401。
8. 浏览器回归验证六种角色的菜单、页面只读状态、拒绝提示、用户开户、授予调整、撤权和审计记录。

### 发布门槛

- `pnpm ts-check`、修改范围 ESLint、相关 Vitest 和 Playwright 用例通过。
- 数据迁移在独立数据库执行，回填前后用户数、成员数、每个默认应用关系和异常清单均可核对。
- 生产切换前由系统、安全、审计三个不同账户完成角色矩阵演练；没有“全权限日常账户”才允许关闭兼容模式。
- 不以页面隐藏、手工数据库修改或环境变量跳过审批作为验收依据。

## 8. 迁移与回滚策略

1. 先发布只新增表、索引、审计字段和只读检查的迁移，不删除 `tenant_memberships`，也不更改既有账户权限。
2. 在隔离环境回填默认应用授予，导出仅含 ID/状态/计数的核对报告；异常数据人工修正后再执行生产迁移。
3. 灰度启用“显式应用授予”认证：先以监控模式记录原逻辑会允许但新逻辑会拒绝的请求，再为缺失授权补齐记录；监控期间不把新逻辑的允许结果反向扩大为授权。
4. 完成角色拆分和首批职责账户演练后，移除 `SYSTEM_ADMIN` 的全权限回退。兼容窗口必须有明确截止版本；窗口结束后遗留 `admin`/`user` 值仅可登录到受限恢复流程，不能自动提升权限。
5. 回滚只回滚应用代码开关，保留新增成员和审计记录；不得删除已产生的授权、审批或审计数据。若出现锁定风险，使用经批准的应急账号流程，而不是直接修改数据库角色。

## 9. 已验证与待实施边界

已运行的针对性回归包含认证、权限拒绝、统一路由安全入口、租户运行时和导出审批，共 9 个测试文件、41 项通过。它证明当前基本认证与部分审批存在，但不覆盖新账户应用授予、同租户跨应用越权、三员互斥或 ABAC，因此不能作为这些能力已完成的证据。

以上 41 项为修复前的历史基线。用户已授权执行后，主要代码、管理 UI、属性授权、可配置 OIDC、审批及运维脚本均已实现；正式企业接入仍需域名、MFA 配置及具名职责人员。最终验证为 1804 项单元测试和 24 组隔离迁移/集成/浏览器场景通过。

实际实施结果、与规划的边界及一项被自动审批阻止的登录计数改进，见同目录《41_IAM权限修复实施与验收记录_2026-09-09.md》。第 8 节为原始迁移规划，当前未执行生产影子流量演练，也不存在可直接恢复旧宽权限的安全回退开关；生产切换以实施记录及部署手册为准。
