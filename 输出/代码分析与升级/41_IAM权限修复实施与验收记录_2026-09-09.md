# IAM 权限修复实施与验收记录

日期：2026-09-09
范围：本地源代码、迁移脚本、管理界面、隔离集成测试及部署配置。

**状态：主要修复已实现并通过隔离验收；未切换现有运行服务。登录计数一致性补丁已获用户明确批准并应用。真实 Keycloak 接入及职责账户引导仍需上线条件。**

## 1. 原因与修复结果

原系统并非完全没有权限设计：已有六种角色、会话版本和路由权限校验。问题在于系统管理员拥有全部权限，职责相互重叠；开户只写用户表，缺少租户/默认应用关系；同租户应用被隐式视为全部可访问；缺少可操作的账户授权界面和企业身份流程。

本轮将动作权限与应用授予分开验证，并补齐审批、会话撤销和部署步骤。

| 范围 | 已实现 |
| --- | --- |
| 三类管理员分工 | 系统管理员管理账户、租户、应用；安全管理员编写和发布策略、进行安全运营；审计管理员独立审批及审计导出。任何日常角色均不再获得全平台权限。 |
| 六种产品角色 | 保留系统管理员、安全管理员、审计管理员、业务操作员、应用开发者、只读用户；提供只读角色权限接口。角色集合固定，不支持任意自定义权限组合。 |
| 显式应用授予 | 登录、范围 Cookie、请求头指定应用和应用列表均校验实际授予；不再因同租户而自动授权。 |
| 账户管理 | 开户、默认应用、授予、身份资料、密码历史及审计在一个事务中提交。编辑采用版本检查；删除转为停用，保留审计引用。 |
| 管理范围 | 不列举或修改未获授租户/应用中的账户；全局身份修改要求覆盖该账户涉及的应用范围。禁止管理员通过管理接口修改自身权限。 |
| 高权限账户审批 | 创建时停用；角色、授权、身份、密码和状态等敏感变更需独立审计管理员批准。绑定参数摘要、申请人/目标版本、期限；拒绝自批、重放、篡改、过期和已撤权申请。 |
| 应急访问 | 默认停用；独立申请后由两名不同角色人员批准，访问窗口 5–60 分钟。每次请求检查到期时间，维护 Worker 自动停用、撤销会话并写入审计。 |
| 模型上线 | 新建或更新模型保持停用；原作者提交版本与配置摘要，审计管理员独立批准后启用。模型凭据引用同样绑定到审批摘要。 |
| 属性授权 | 允许环境、最高应用数据分级、应用所属部门、用途、用户组和到期时间。授予不能超出操作者自己的属性和有效期边界。 |
| 凭据隔离 | 应用开发者仅列举和撤销自己创建的应用凭据；服务凭据仍只有限定的护栏/应用接入权限。 |
| 管理界面 | 新增账户与授权、授权审批页面；可编辑属性授予。菜单及直接页面访问按角色限制；IAM 与模型审批展示参数明细，原有白名单、词典、模板、发布和导出审批保留原页面入口。 |
| 企业登录 | 采用 Keycloak + OIDC 方案；授权码、PKCE、nonce、浏览器绑定、一次性 state、签名/签发者/受众/期限和强制 MFA ACR 校验。只匹配预先绑定的 issuer + subject。 |
| 运维交付 | 提供只读预检、缺失职责引导、到期维护命令、Keycloak 部署模板；主 Compose 已增加迁移挂载和每分钟 IAM Worker。 |

属性授权当前以显式应用为资源边界，部门约束指应用所属部门。它不是自动从员工自助资料推导的组织权限，也不等同于已完成所有历史数据逐条重新分级。

关键场景包括：

1. 已有成员只回填原默认应用；重复迁移不恢复已撤销授予。
2. 开户后能登录并完成实际首次改密；跨应用开户失败不留记录。
3. 同租户未授予应用、跨租户作用域、伪造应用请求头均拒绝。
4. 账户管理列表与修改不能跨越操作者应用范围。
5. 高权限创建先停用，再由独立审批启用；重复审批拒绝。
6. 停用后旧 Bearer 和原先有效的范围 Cookie 失效。
7. 参数篡改、目标版本变化、申请人撤权后的审批均拒绝。
8. 应急启用要求两名不同角色；到期立即拒绝访问，维护任务实际将账户停用。
9. 模型上线独立审批、版本绑定和二次执行拒绝。
10. 使用真实 RSA 签名的隔离 OIDC 签发者，验证成功登录以及 MFA、受众、nonce、到期、伪造签名、浏览器绑定和重放反例。
11. OIDC 身份重复绑定在已写入用户和授权之后失败，整个事务回滚。
12. 全部 ORM 表列与迁移后数据库一致。
13. 六种角色的页面与菜单边界，系统管理员从实际界面开户，审计管理员加载并展开真实变更快照；页面不显示密码哈希。

测试使用全新临时 PostgreSQL 容器、本机 58889 临时应用服务和虚构 iam.* 用户，未连接运行中的业务数据库。测试结束清理自行创建的容器和服务。此结果不能替代真实 Keycloak、TLS 代理和组织 MFA 流的部署验收。

## 4. 现有环境及上线前置条件

对运行中的 guardllm-r0 环境只进行了只读检查：

- 当前有 2 个活动 SYSTEM_ADMIN。
- 尚无 SECURITY_ADMIN 和 AUDIT_ADMIN。
- 活动用户缺失活动租户成员关系的计数为 0；这不是完整数据预检结果。
- 尚未应用新的 user_application_memberships 迁移。
- 应用容器未挂载工作区源代码，仅只读挂载策略公钥；本地编辑与构建未改变运行服务。

因此未执行生产迁移、创建正式职责用户或切换应用镜像。正式上线顺序：

1. 备份数据库并运行完整只读预检，核对异常默认应用及额外应用需求。
2. 应用 0073、0074，核对回填；原有成员关系和审计数据保留。
3. 为实际不同人员引导缺失的安全和审计职责，完成首次改密及权限演练，再切换新应用。
4. 配置企业登录域名、TLS、Keycloak realm/client、两因素认证及 subject 绑定；验证后启用管理账户企业登录要求。
5. 启用 IAM Worker，核对定时维护及应急账户保管责任人。
6. 核对已有模型配置并安排首轮复核。迁移不自动停用已有模型；后续新建/修改按新上线审批流程执行。

回退前关闭业务入口并恢复经过验证的代码/数据库配对状态，保留授权和审计证据。不能直接回退到旧的全权限管理员语义继续运行。

## 5. 登录计数一致性修复

已将现有登录条件检查从 src/app/api/auth/login/route.ts 后半段前移到 src/lib/auth/login-service.ts 的成功计数更新之前，并让路由区分“登录方式不符”和“作用域不可用”的结果。

改动范围：

- 验证口令与角色后，先检查已有身份档案、企业/应急登录方式及有效默认应用。
- 条件符合才调用 recordSuccessfulLogin。
- 不修改企业登录环境开关，不部署到运行服务，不替代上线前的职责账户引导。

修复效果：被身份、企业/应急登录方式或应用范围检查拒绝的口令尝试，不增加 loginCount、不更新 lastLoginAt，也不清空已有失败次数。成功的本地登录正常增加计数。新增数据库回归覆盖身份缺失、OIDC 专用账户、过期应急、强制企业登录及撤销授予五种反例，并验证拒绝响应不签发 Cookie。

用户在本任务中明确回复“批准”后，已完成此本地源码补丁。登录准入条件保持一致，未修改运行环境或部署服务。
