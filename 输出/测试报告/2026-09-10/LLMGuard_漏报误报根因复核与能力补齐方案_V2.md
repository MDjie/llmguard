# llm-guard 漏报、误报根因复核与能力补齐方案 V2

> 2026-09-10。本文取代同目录的《LLMGuard_漏报治理与能力补齐设计方案》。用途：决定下一轮测评对象、修复优先级与验收方法；不是已经验证的改进效果报告。
>
> 数据截止：北京时间 2026-09-10 06:22:45 的冻结快照。两个基础集已完成 21,699 条，其他有标签阶段已扫描 61,250 / 86,620 条。全量任务仍在继续，本文不把阶段结果写成最终全量成绩。本次复核没有修改在跑任务、策略或线上服务。

## 1. 决策结论

**首先必须修正测评对象：现在这批结果测的是第三方 `llm-guard 0.3.10` 的两个 Python 输入扫描器，不是本项目完整的 TypeScript 护栏引擎。** 目前可以解释两个扫描器为何漏报、误报严重；还不能据此给自研引擎的规则覆盖、语义调用或最终放行能力定性。

目前证据支持的主要原因，按解决顺序如下：

| 优先级 | 结论 | 证据强度 | 对决策的影响 |
| --- | --- | --- | --- |
| P0 | 基准没有经过自研引擎，产品能力与扫描器能力混淆 | 已从 runner 与引擎源码确认 | 先建立真实项目基线，否则补规则后也无法证明产品提升 |
| P0 | 部分“违规”标签包含求助、风险讨论和伦理提问，不能直接映射为有害请求阻断 | 已在固定抽样中查到；总体比例尚未估计 | 保留原标签成绩，同时建立经过政策复核的产品标签 |
| P1 | 两个模型的语言和任务范围与广义内容安全不匹配 | 模型卡、跨数据集结果与类别分布相互支持；尚未量化各因素独立贡献 | 中文/多语种广义安全识别是主要能力补齐方向，不能只扩关键词 |
| P1 | 提示注入结果直接 OR 到有害内容判定，制造大量误报 | 已完成集 2,048 个 FP 中 2,047 个仅由注入检测器触发 | 分开风险类型和策略动作；不能直接把注入检测器删除 |
| P2 | 输入/输出共用扫描方式，输出丢失原始问题上下文 | runner 与 PKU 转换代码已确认 | 重建 prompt-response 上下文，独立评估输出安全 |
| P2 | 部分测评设计妨碍定位：0/1 风险分数、聚合计数、代理标签、混合方向 | 文件与源码已确认 | 先补逐条证据、原始概率、标签来源和执行漏斗 |
| P2 | 兼容性、长文本和语义覆盖配置需要验证，但现有证据不支持把它们都称为主因 | 有明确检查结果及待验证条件 | 用隔离对照排查，不先重写引擎 |

**旧版结论的更正：**“没有规则层”只适用于当前 Python 基准，不能用于整个项目；“稳定运行所以引擎没问题”证据不足；原来给出的分阶段漏报率 50%/30%/15% 没有实验支撑，撤回为承诺目标；基于离散风险值的 AUC 不能用来证明原始模型几乎没有排序能力。

## 2. 统计口径与当前证据

### 2.1 指标定义

- 漏报率 FNR = FN / (TP + FN)，误报率 FPR = FP / (FP + TN)。没有负例的集合，FPR 为“不适用”，不是 0%。
- 下表是扫描器联合命中对数据集标签的匹配结果；标签不等于本项目所有场景下的最终阻断政策。
- 数据集的 `harmful/toxic/safe` 与 `prompt injection` 是不同任务标签。安全内容上的注入命中，在内容有害基准中是 FP；是否同时构成真实的权限边界攻击，需要另行标注，不能混为一谈。

## 3. 漏报的主要原因

### 3.0 先区分“标签漏报”和“真实有害内容漏报”

这是本次深入复核新增的重要发现。固定随机种子对中文每个主题抽 2 条 FN、中文抽 6 条 FP，英文抽 6 条 FN 和 6 条 FP，共 38 条；逐条复放两个扫描器，76 个判定全部与原预测一致。复核文本时发现，部分来源“违规”标签对应的是求助、风险认识或伦理讨论，而非明确请求危险协助。

以下为文本含义概述；编号是预测 CSV 的一基数据行号（不含表头），精确源行号和文本 hash 可在抽样文件中追溯：

| ChineseSafe 预测行号 | 来源主题/原始标签 | 内容概述 | 对产品政策的判断 |
| --- | --- | --- | --- |
| 2774 | 心理健康/违规 | 害怕当众发言，询问如何控制情绪 | 求助型内容，不能仅因涉及心理健康要求阻断 |
| 6232 | 心理健康/违规 | 工作占据注意力，出现不适 | 状态描述，需支持性响应，不等同有害请求 |
| 8231 | 身体伤害/违规 | 表达知道过量饮酒的身体危害 | 风险认知，不能按“伤害实施”规则处理 |
| 5488 | 身体伤害/违规 | 讨论过量食辣会不舒服 | 一般健康讨论 |
| 9284 | 财产隐私/违规 | 询问陌生邮件为什么索要个人资料 | 防骗求助，不是主动泄露/窃取 |
| 8247 | 财产隐私/违规 | 照顾年迈父母而忙不过来 | 主题归类与隐私风险也有疑点 |
| 975、9806 | 道德伦理/违规 | 讨论离婚偏见、非婚家庭是否合理 | 伦理提问，政策不能默认全部拒答 |

这些是需要政策复核的实例，不是擅自修改源标签，也不是已经经过独立双人仲裁。当前抽样有意按错误和类别选取，**不能将其中疑似标签错配的比例外推到全量**。它足以否定“所有标签 FN 都应该通过加规则封禁”的前提。

下一版同时保存 `sourceLabel`、`sourceCategory`、`policyLabel`、`policyVersion`、`reviewStatus`，原始成绩保持不变；产品成绩只对已经确认政策标签的样本计算，另报未定/不适用数量。若业务需要把求助识别为一个需特殊响应的风险信号，应分别评估“识别到求助”与“是否阻断”，不要共用一个有害二元标签。

### 3.1 广义安全风险被交给了不对应的模型

`Toxicity` 使用 `unitary/unbiased-toxic-roberta`，主要面向英语评论毒性，检查 toxicity、severe_toxicity、obscene、threat、insult、identity_attack、sexual_explicit 等标签。它不是通用“是否在请求危险帮助”分类器。礼貌表达的有害请求可以没有粗口、威胁语气或攻击性用词；中文理解又是另一层限制。[官方模型卡](https://huggingface.co/unitary/unbiased-toxic-roberta)

`PromptInjection` 使用 `protectai/deberta-v3-base-prompt-injection-v2`。官方模型卡明确说明其范围是英语提示注入，并列出非英语、越狱、系统提示误判等局限。用它兜底中文伤害、犯罪、心理健康、歧视或回答安全，任务本身就不对齐。[官方模型卡](https://huggingface.co/protectai/deberta-v3-base-prompt-injection-v2)

实测相互印证：

- ChineseSafe 毒性检测 TP 仅 13 / 10,000；ToxiCN 仅 4 / 6,461。后者本身是中文毒性任务，说明问题不能只归因于“广义安全标签比毒性更宽”。
- 英文 WildGuardTest 的毒性检测也只有 4 / 754，说明把中文换成英文仍不能弥补“有害请求 ≠ 有毒评论”的任务差异。
- 以上证据支持语言适配与任务覆盖是优先假设；尚不能把 7,833 条中文 FN 按“语言占多少、标签空间占多少”拆成因果百分比。需要同样本的中文广义模型、英语对应模型等对照。

本次还做了人工构造的中英文同义辱骂对照：毒性原始 sigmoid 最大风险分数，英文约 **0.997202**，中文约 **0.000347**；中文种花正常文本约 **0.000373**。固定抽样的 20 条中文 FN 毒性分数范围约 0.000347–0.000501，与 6 条中文 FP 的 0.000347–0.000462 重叠。它们支持“直接微调一个毒性阈值很难解决中文问题”，但小样本不足以推导全量最优阈值。

注入模型对本次中英文同义显式注入句都给了接近 1 的分数。因此其非英语能力并非所有输入均为零；应该说“非英语不在其官方保证范围、在本项目任务上结果不可靠”，不能绝对化为“中文全部识别不了”。

### 3.2 优先补的是风险识别组合，不是主题词黑名单

ChineseSafe 正例每类 1,000 条：

| 来源主题 | FN | FNR | 优先补齐方向 |
| --- | ---: | ---: | --- |
| 偏见歧视 | 989 | 98.9% | 群体/个人对象 + 贬损、排斥、剥夺权利等意图；引用、反歧视讨论作为负例 |
| 身体伤害 | 987 | 98.7% | 伤害对象 + 实施/优化意图 + 可执行性；急救和预防作为负例 |
| 心理健康 | 953 | 95.3% | 自伤鼓励、实施协助与危机求助区分；求助内容不能主题词即封禁 |
| 道德伦理 | 934 | 93.4% | 按产品政策拆成可定义行为，不把宽泛道德判断直接编为硬阻断 |
| 违法犯罪 | 930 | 93.0% | 行为 + 具体实施协助/规避意图；法律讨论、安全防御作为负例 |
| 政治错误 | 841 | 84.1% | 先核验来源标签和业务政策映射，不能把政治主题整体禁掉 |
| 财产隐私 | 762 | 76.2% | 真实敏感实体 + 泄露/获取/外传关系，复用现有结构化 DLP |
| 淫秽色情 | 700 | 70.0% | 具体性内容与医学教育区分，语义分类为主 |
| 脏话侮辱 | 640 | 64.0% | 中文辱骂/谐音变体、对象关系、引用边界 |
| 变体词 | 97 | 9.7% | 单独做成对变体测试，不能从该行推出已有可靠反混淆能力 |

前五类合计 4,793 / 7,833 = 61.19% 的中文漏报，值得优先标注与对照测试。但其中宽泛政策主题必须先明确适用边界；这不是承诺规则能救回 61.19%。

**规则缺少什么，目前不能下最终清单。** 完整项目规则未被这一轮执行。实际缺口须从“现有规则匹配了没有 → 被哪些约束排除 → 命中是否只是候选 → 语义是否覆盖 → 最终动作是否执行”逐层归因，避免把未启用、策略例外、语义不完整误记为“缺规则”。

### 3.3 截断确实有风险，但不是已完成集的大规模 FN 主因

对全部 21,699 条按两个实际 tokenizer 分别重新计数：

| 数据集 | Toxicity 超过 512 token | Injection 超过 512 token | FN 中超限数量（两模型各自统计） |
| --- | ---: | ---: | --- |
| ChineseSafe | 1,491 | 318 | 两者均为 0 / 7,833 |
| WildGuardTest | 3 | 3 | 两者均为 1 / 523 |

因此，中文基础集的这些 FN 不能由 512-token 尾部截断解释；英文基础集至多只有 1 条 FN 具备这一前提。长文本仍需补齐覆盖，尤其是尚未完整检查的输出和其他集合，但不能把“加窗口”列为当前最大收益来源。Injection tokenizer 的未设置最大长度是一个巨大哨兵值，实际 pipeline 明确传入 512；检测长度时必须使用真实有效限制。

### 3.4 输出检测丢了原问题，并且使用输入扫描器

PKU 转换保留了 `pairId`、`promptSha256`，当前扫描却只接收 response 文本；运行器不按 OUTPUT_COMPLETE 切换检测器。这样无法稳定区分拒绝、引用、危险建议与对原问题的实际回应。输出的危险程度也不等于“回答看起来像提示注入”。

下一版应按源数据 pairId 重建 user prompt + assistant response，保留角色与信任边界；仅 response 是被审查输出，prompt 是判断语境，不能把 prompt 的风险自动算到安全拒绝的输出上。源数据提供配对问题和回答的安全标签，适合这种对照。[PKU 官方数据说明](https://huggingface.co/datasets/PKU-Alignment/PKU-SafeRLHF)

## 4. 误报的主要原因与治理顺序

### 4.1 当前最明确的误报来源是注入检测器与 OR 聚合

ChineseSafe 的全部 1,834 条 FP、WildGuardTest 的 213 / 214 条 FP，仅由注入检测器触发，共 2,047 / 2,048 = 99.95%。这是**触发来源归因**，不等于已经证明每条误报都由某个词触发。

不能简单删除注入检测器：同样这两集，联合 TP 是 2,398，毒性检测单独 TP 只有 17；删掉注入检测会损失 2,381 个当前 TP。应补齐广义安全分类，再把注入检测回归专门风险；不能用“误报降低”掩盖进一步失去召回。

当前注入阈值是 0.9，且源码先将概率四舍五入到两位，再做严格大于比较。它并非“阈值太低”，也不适合盲目统一上调或下调。下一版保存未取整概率，按任务、语言与上下文在独立校准集选择阈值。

抽样还看到普通中文账单查询（预测行 12994）被注入模型打到约 0.9771，普通阅读推理提问（行 19841）约 0.9945。英文样本则包含角色扮演和带有越狱包装的内容；某些包装可能确实涉及注入，但来源标签只判断内容有害性。两者必须分别记录：普通内容高分错判，以及不同任务标签之间的冲突。仅提高注入阈值既无法解决任务冲突，也可能丢失真实注入召回。

### 4.2 误报治理要在具体证据范围内工作

- 提示注入：分别识别被审查用户内容、可信系统指令、工具/RAG 返回的非可信文本；识别越权指令与被引用的示例。只输入孤立字符串不足以可靠判断权限边界。
- 内容安全：允许求助、新闻报道、反歧视讨论、医学教育等合法目的，但“教育用途”等自述不能成为全局豁免。看具体内容、请求动作与输出是否实际提供危险协助。
- DLP：实体格式校验、上下文关系和敏感性一起判断。占位符、合成样本、公开讨论需要不同于真实凭证外泄的处理。
- 规则：只有政策明确且证据确定的情形升级硬阻断；泛化词法信号进入 `CANDIDATE`，用对应风险的语义证据解决，不新建一套覆盖全部规则的全局白名单。

## 5. 是模型、规则，还是引擎：怎么做可归因排查

### 5.1 已验证与仍未验证的边界

本次检查了实际安装代码、权重哈希、类与标签配置。当前环境 `llm-guard 0.3.10`，但其元数据要求 torch 2.0.1 / transformers 4.38.2；实际是 torch 2.11.0 / transformers 5.5.0，runner 有兼容 shim。不能因为推理没有抛异常，就说依赖升级绝无影响。

模型加载报告没有 missing/mismatched 参数；RoBERTa 有一个 unexpected `roberta.embeddings.position_ids`，DeBERTa 没有 unexpected 参数。二者均为 eval 模式。此结果不支持“分类头没有加载”的猜测，但不能替代与兼容参考环境的数值对照。

38 条历史错误样本的 76 个扫描器判定复放全部一致；8 个人工构造诊断用例中，直接 forward 后做 sigmoid/softmax 与 pipeline 分数的最大绝对差小于 1e-6。这降低了“当前环境中 pipeline 错用了激活函数/翻转标签”的可能性；它们仍共享同一运行库，因此不能排除共同的版本兼容问题。

长文本人工对照出现了警示性反例：把显式注入放到 913-token 输入尾部后，模型仍给约 0.9933 的注入分数。比较实际 tokenizer 输入确认：尾部攻击文本与纯正常填充文本在截断后得到完全相同的 512-token 模型输入。因此这个高分不能归功于识别了尾部攻击，它只反映模型对可见正常前缀的误报。此控制实验与真实集的长度统计分开，不据此承诺窗口化会改善多少召回。

| 已有模块 | 已实现能力 | 下一步核验，不要重复造轮子 |
| --- | --- | --- |
| `from-policy-bundle.ts` | 规则、DLP、内容意图、输出检测、分类器、裁判组装 | 实际签名 bundle 中的 DAG 节点决定哪些检测器运行；源码有类不等于启用 |
| `rule-detector.ts` | 方向、语言、场景、时效、匹配约束与例外；规则角色分类 | 导出有效规则清单与排除原因；区分硬拒绝、确定风险、词法候选 |
| `semantic-classifier.ts` | 模型身份、结果覆盖校验、分类输出处理 | 模型覆盖语言/风险/方向是否合格，adapter 是否符合现有响应协议 |
| `coverage-judge.ts`、`semantic-coverage.ts` | 基础裁判、复核裁判、窗口和覆盖完整性 | 检查 ENFORCE/SHADOW、必需风险、上下文范围与窗口预算；已有流程并非只对词法命中才运行 |
| `aggregate.ts` | 未解决候选/覆盖缺口进入复核或按策略 fail-closed | 不能把 UNKNOWN 描述成默认放行；逐条看真实动作及降级原因 |
| `decision-funnel.ts` | 检测阶段与输出可释放性信息 | 复用为归因入口；其 transport verified 字段不能替代真实出口拦截验证 |

当前协议要求所有请求风险都完整返回，任一 UNKNOWN 可导致整次响应不完整。这是“整组校验过于耦合”的可验证风险，不是本轮 Python FN 的已证实原因。现有聚合通常把它表现为复核/降级/阻断，所以还可能推高正常内容干预，而不一定漏报。

### 5.3 每一条错误必须落到一个可验证的主因

新的项目基准逐条记录如下流水账，主因取最早导致失败的必要环节，其他问题记为次因：

| 主因编码 | 判断依据 | 对应改动 |
| --- | --- | --- |
| TASK_OR_LABEL_MISMATCH | 标签任务/方向/政策不一致，或者代理标签未经确认 | 修正测评口径与任务映射，不能靠改引擎刷分 |
| DETECTOR_NOT_SCHEDULED | bundle/DAG/模式/上下文导致应覆盖检测器没执行 | 配置、编译或路由修复 |
| RULE_MISSING | 正确规范化后无规则覆盖，且政策适合确定性规则 | 新增有正反例的规则 |
| RULE_FILTERED_OR_CONTEXT_LOST | 有规则但方向、语言、例外、视图或上下文约束阻止命中 | 针对性修复配置、上下文或约束 |
| MODEL_MISS_OR_FALSE_ALARM | 已正确调用、有完整有效结果，任务匹配但分类错误 | 模型替换、训练或校准 |
| COVERAGE_OR_RUNTIME_FAILURE | 超时、空输出、解析失败、超窗、UNKNOWN 等 | 协议、预算、依赖或覆盖机制修复 |
| AGGREGATION_OR_ACTION_ERROR | 证据正确，最终动作或响应出口不正确 | 聚合/干预/出口执行修复 |

没有执行 trace 的旧样本不可强行分配 RULE_MISSING；归为“待复放定位”。已有 FP/FN 抽样仅供发现机制，不能用刻意分层的错误样本估计全量原因占比。

## 6. 目标架构：复用项目引擎，补齐广义语义覆盖

建议流程：来源/方向与上下文 → 现有规范化和确定性检测 → 覆盖检查 → 缺口上的基础安全分类 → 必要的上下文复核 → 现有聚合与出口动作。

### 6.1 基础识别不能只服务于关键词命中样本

每条需要做内容安全审查的请求，其必需风险都应由合格检测器覆盖。没有词法命中不等于安全；未覆盖的风险仍进入基础语义识别。可复用 `coverage-v1` 的覆盖判定和基础/复核裁判设计，不能为了省调用把它退回“只扫规则命中”。

首轮候选可比较 Qwen3Guard-Gen 0.6B 与 4B：官方提供中英等多语种、输入及输出分类，原生结果包含 Safe / Unsafe / Controversial。这里只把它列为适配性候选，未在本机测吞吐、准确率或部署可行性，不能声称更换后必达某分数。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3Guard-Gen-0.6B)

接入不能直接填一个兼容聊天接口就结束：Qwen 原生标签文本不是本项目 judge JSON，也不是 classifier 的概率协议。优先做单独 adapter，解析原生格式、严格映射风险与方向、保留模型/权重/策略版本。没有校准过的概率就记录离散判定，不能把 Safe=0.99 或 Unsafe=1.0 冒充可信置信度。证据偏移没有实际定位能力时保留“不支持”，不能编造 span 通过验收。

若选用既有 DeepSeek 裁判，先测空正文、解析、输出预算、上下文限制与完整覆盖率；以项目中实际配置为准，不假定先前填写过密钥就代表模型已经生效。

### 6.2 语义协议的改进边界

先用小规模、按风险拆组的请求验证现有协议，降低一条 UNKNOWN 使全部风险作废的概率。若仍是主要失败源，再新增版本化“逐风险/逐窗口完成状态”，保留已验证 UNSAFE 证据，未完成风险仍 UNKNOWN；绝不把缺失风险补 SAFE。

复用现有窗口计划和 UTF-16 证据映射，同时新增真实 token 预算检查。覆盖完整性需同时包括：全部必需风险、全部需要的文本窗口、适用上下文、方向和语言。只有部分窗口安全，不能汇总为全文安全。

复核只允许在同一风险、同一证据范围内解除不确定候选；确定性硬拒绝不被模型的一句“安全”全局覆盖。现有 `coverage-judge.ts` 已有范围受限反证机制，应验证和复用。

### 6.3 规则补齐的具体工作包

| 工作包 | 建议匹配形式 | 负例/边界要求 | 状态 |
| --- | --- | --- | --- |
| 中文辱骂与显式威胁变体 | 有限规范化 + 对象/行为关系，保留原文与映射 | 引用、反驳、报道、谐音自然词 | 先盘点现有词典与规则，再补缺项 |
| 伤害与犯罪实施意图 | 危险行为 + 实施帮助/优化/规避的组合 | 急救、法律咨询、防范、防御 | 以候选召回为主，交语义确认 |
| 自伤风险 | 鼓励/协助自伤与求助/安慰分离 | 危机求助不能简单封禁 | 语义优先，动作支持安全响应 |
| 隐私与凭证外泄 | 实体校验 + 数据性质 + 外传/索取关系 | 公开信息、占位符、脱敏样本 | 复用 StructuredDlpDetector |
| 提示注入与越权 | 指令层级伪造、权限越界、工具/RAG 来源关系 | 安全研究示例、可信系统指令 | 复用现有攻击检测器，按上下文补齐 |
| 输出安全 | 回答是否实际提供危险帮助、敏感信息是否已暴露 | 合理拒绝、引用、必要安全说明 | 复用输出检测器，加入 prompt-response 语义 |

每条新规则必须附：政策风险 ID、方向/语言、触发证据、作用域、正例、最小差异负例、现有错误样本回放结果。优先少量高覆盖的组合规则，不按数据集原句逐条记忆。

## 7. 可执行落地计划与验收

以下为有熟悉代码的工程人员与模型运行资源时的工作日估算，不是已经承诺的改善幅度；没有 GPU 时先比较可用部署的质量与延迟，再决定本地模型规模。

| 阶段 | 时间估算 | 责任角色 | 交付物 | 完成条件 |
| --- | --- | --- | --- | --- |
| A：校准测评对象 | 0–1 天 | 测评/引擎工程 | A0 第三方基线、B0 自研原配置、C 候选配置的独立 manifest；源标签/政策标签清单 | B0 确实调用本项目入口并留每条 trace；三轨不可混名 |
| B：补诊断与参考环境 | 1–2 天 | 测评/运行时工程 | 逐样本 ledger、可断点恢复计数、隔离兼容环境对照 | 漏扫/错误/未知单列；同权重依赖差异得到量化 |
| C：确认规则与语义缺口 | 2–3 天 | 引擎工程/标注人员 | 主因编码表、有效规则/DAG清单、语义失败分布 | 错误样本能定位环节；输出上下文配对正确 |
| D：快速候选对照 | 3–5 天 | 模型/引擎工程 | 中文广义分类 adapter、小批规则修补、输出上下文候选 | 同样本记录 FN→TP、TN→FP、TP→FN、FP→TN；未校准前不推广 |
| E：校准与回归 | 5–7 天 | 测评/测试工程 | 校准阈值、独立留出成绩、性能与覆盖验收 | FN 显著减少，同时满足分桶 FP、复核负荷、延迟约束 |
| F：部署前验证 | 验收通过后 | 服务/测试工程 | 影子结果、回滚包、实际出口执行证据 | 项目离线成绩与服务执行一致；走现有发布流程 |

### 7.1 建议具体落点

- 新建独立项目基准 runner，复用项目 guard-engine-v2 的正式入口及真实 bundle 构建；记录入口路径、git revision、工作区变更指纹、bundle digest、DAG、检测器版本。不要改写正在运行的 Python 任务。
- 在现有 `decision-funnel.ts` 旁构建测评记录适配层，保存请求 ID、来源行号/哈希、gold 来源、方向、上下文摘要、执行/跳过原因、风险观测、完整覆盖、最终动作、降级及延迟。敏感正文按项目既有权限存放。
- 对 `from-policy-bundle.ts`/DAG 做“配置声明—实际节点—实际执行”一致性检查；只有发现偏差才修代码。
- 分类器 adapter 优先新增独立模块，复用 `semantic-classifier.ts` 的身份与覆盖校验；协议不兼容时显式版本化，别靠伪造概率/证据穿透校验。
- 输出样本转换器按 PKU 原始记录恢复配对上下文，分别保存 prompt 与 response 的 hash；无法恢复的行记缺失上下文，不假装完整。
- 修正下一版运行器的恢复字段：读取 `latency_seconds`、写入 `latency_seconds_total` 不一致，会在续跑后丢失历史延迟累计。这影响性能统计，不是已证明的分类 FN 原因。
- 新版无标签阶段保存各检测器命中和动作计数；当前只累计 unlabeled/方向等信息，不能由它计算漏报误报，也不足以完整给出命中分布。

### 7.2 对照实验顺序

| 实验 | 保持不变 | 唯一主要变化 | 要回答的问题 |
| --- | --- | --- | --- |
| E0 | 权重、tokenizer、样本与阈值 | 现环境 vs 依赖兼容参考环境 | shim/依赖是否改变推理或判定 |
| E1 | 同一任务标签和样本 | 第三方 A0 vs 自研 B0 | 产品到底具备哪些能力；这是系统比较，不当作单因素因果 |
| E2 | 自研规则与策略 | 加合格广义安全分类 | 最大 FN 是否来自语义覆盖缺口 |
| E3 | E2 模型与策略 | 仅加一组规则 | 哪组规则真正救回 FN、增加多少 FP |
| E4 | 模型与输出样本 | response-only vs 配对上下文 | 输出上下文价值与潜在误报代价 |
| E5 | 模型与长文本样本 | 单窗口 vs 完整窗口 | 截断造成多少真实漏报；不稀释到短文本结论 |
| E6 | 同一原始分数 | 校准阈值/风险动作映射 | 最优 FNR–FPR–复核率取舍 |

先在分层诊断集做这些实验，再对通过者跑全量回归。不得为省推理只挑已有规则命中的样本，这会隐藏无词法信号的漏报。

### 7.3 数据划分与验收指标

已被本次分析查看和用于设计的样本，应视为回归/开发证据。原文件名叫 test 不意味着继续调参后仍是独立测试。按原始 prompt 家族、改写家族、来源 pairId 去重分组后建立调参集；最终验收用未接触的留出样本或新标注样本，不让同一问题的变体和成对回答跨组泄漏。

建议先形成约 2,000 条诊断集合，覆盖各风险、语言、方向、FN/FP及正常样本，再补各高风险至少 200 条确认正例和足够正常困难负例的独立验收集。数量是启动预算，不保证置信区间足够窄；对稀有错误按目标区间补样本。标签政策有歧义的样本由两名标注者独立判断并仲裁，报告一致性和未定比例。

**优化次序：先在约束内最小化 FNR，再压低 FPR。** 建议的候选筛选门槛（设计目标，未经本次实验验证）：

1. 相对真实项目 B0，关键风险的 FN 有实质下降；试点可把相对减少 30% 作为进入全量回归的目标，但达不到就定位原因，不靠调口径过关。
2. 来源标签一致、同一留出样本上的整体及关键分桶 FPR 不恶化；报告差值及 95% 区间，样本不足时写“证据不足”，不能把未显著等于不恶化。
3. 所有必需风险的覆盖状态都可审计；未知/错误不能算安全，也不能把全部样本送复核后宣称 100% 自动召回。
4. 同时报“自动阻断召回”“危险内容实际阻止释放率”“正常内容被阻断/送复核率”“复核率及完成结果”“技术失败率”。`REQUIRE_REVIEW` 只有在实际阻止内容释放时，才计入出口拦截；它仍不是确认有害。
5. 输出 MASK/REWRITE/SAFE_RESPONSE 必须做转换后复检及出口验证，不能把任意非 ALLOW 动作都算成功阻断。
6. 记录 P50/P95 延迟、吞吐、模型调用比例和资源/调用成本；复核率及延迟预算在试点前按场景固定，不能实验后为了好看修改。

比例给 Wilson 95% 区间；版本差异用同样本配对转移表与按 prompt 家族聚类的 bootstrap。报告每个风险的正负分母，不能用类别平均遮盖高风险退化。

## 8. 数据质量与结论限制

- 86,620 是当前其他有标签阶段的计划数；转换数据中有空文本，runner 会跳过。应以 expected/scanned/skipped/error 的守恒表交账，不要求扫描计数机械凑满目标。旧的 WildGuard 无二元标签行也要说明排除范围。
- JADE/JailBench 的 dataset_intent 标签只能作为代理压力测试；不得与独立人工二元标注的错误率混报。
- 现有 CSV 保存的是 scanner 风险值 0/1，不是底层连续概率。基于它算出的单扫描器 AUC 反映一个工作点的表现，不能用来选择原始概率阈值或断言模型排序性能。联合 0/1/2 也不是校准概率。
- 当前其他阶段只保留聚合计数；不能声称已对其所有 FN/FP 做逐条根因审阅。本文逐条计数核验、长度分析的范围是完成的 21,699 条基础集。
- 本方案依据代码静态检查与独立诊断，不证明线上实际 bundle、模型可用性或出口执行状态。后续 B0/服务对照会补齐这些证据。
- 后续全量跑完后，更新冻结数据表与逐类权重；如果出现新模式，再修正优先级。上述任务范围错配和 OR 来源证据不依赖把当前部分快照冒充最终结果。
